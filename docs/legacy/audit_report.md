# Глубокий Структурный Анализ NeuroSupply (v2.0)

**Дата:** 1 Февраля 2026
**Статус:** Анализ несоответствий (Gap Analysis)
**Основание:** Спецификация Бизнес-Логики v1.0, Google Sheets Integration

---

## 1. Резюме Соответствия (Executive Summary)

Проект **NeuroSupply** технически реализован как модульный монолит, готовый к масштабированию. Однако, текущая реализация **значительно расходится со Спецификацией v1.0** в ключевых узлах бизнес-логики.

| Компонент | Текущая Реализация | Требование Спецификации v1.0 | Статус |
| :--- | :--- | :--- | :--- |
| **Источник Плана** | Google Sheets (хрупкий парсер) | Google Sheets (основа знаний) | ⚠️ Требует переработки |
| **Горизонт Планирования** | 1 день (передается float) | **Завтра + Послезавтра** (сумма) | 🔴 Блокер |
| **Формула Расчета** | `(Plan/1000 * Mix) - Stock` | `(Plan/1000 * Mix * 1.1) - Stock - Transit` | 🔴 Критический баг |
| **Единицы Измерения** | КГ/Литры (округление 0.01) | **Коробки/Упаковки** (авто-округление) | 🟡 UX проблема |
| **Верификация** | WebApp (Generic) | WebApp + Выбор причины аномалии | 🟡 Частично готово |

## 2. Анализ Узлов (Component Analysis)

### 2.1. Источник Данных: Google Sheets
**Код:** `src/services/data_loader/sales_plan_parser.py`
**Текущее состояние:**
*   Парсер использует эвристику: ищет строку с числами `1, 2, 3...` для определения дней.
*   Ищет ключевые слова "План", "Выручка".
*   Полагается на жесткую структуру, которая может не соответствовать новой таблице пользователя.

**Риски:**
*   Новая таблица (ссылка пользователя) может иметь сложную "шапку", объединенные ячейки или другую структуру дат. Текущий парсер, скорее всего, вернет пустой список или ошибку.
*   Нет валидации формата данных (что если в ячейке формула?).

### 2.2. "Мозг" Системы: Calculation Engine V2
**Код:** `src/services/calculation/engine_v2.py`
**Выявленные Гэпы (Gaps):**

1.  **Отсутствие Страхового Запаса (Safety Stock):**
    *   *В коде:* `dish_needs` считается напрямую от плана.
    *   *В спеке:* Требуется множитель `1.1` (или настраиваемый параметр безопасности).
    
2.  **Игнорирование Товаров в Пути (Goods in Transit):**
    *   *В коде:* `order_qty = need - current_stock`.
    *   *В спеке:* `order_qty = need - current_stock - transit`.
    *   *Проблема:* Если мы вчера заказали 100кг мяса, и они еще не приехали, система сегодня снова закажет эти 100кг, создав затоваривание (Overstock).

3.  **Проблема "Packaging" (Коробки vs КГ):**
    *   *В коде:* `round(order_qty, 2)`.
    *   *В спеке:* Повар должен видеть "4 коробки", а не "34.5 кг".
    *   *Решение:* Необходимо использовать поле `Product.package_size` для деления и округления `math.ceil()`.

4.  **Горизонт Планирования:**
    *   Функция `calculate_needs` принимает `sales_plan_rub`. Это скаляр. Вызывающая сторона (`main.py` или `cron`) должна уметь суммировать планы на N дней вперед. Сейчас механизма суммирования "Завтра + Послезавтра" в явном виде нет.

### 2.3. Верификация: Telegram Bot & WebApp
**Код:** `src/bot/handlers.py`, `src/services/order_service.py`
**Логика:**
*   Бот отправляет ссылку на WebApp. Это правильно (UI сложный).
*   **Обработка Аномалий:** В `order_service.py` есть проверка `abs(new - old) > 0.01`.
*   **Проблема:** Причина аномалии хардкодится: `reason="Manual update via API"`.
*   **Требование:** Frontend должен передавать `confirm_payload` с причиной (например, "Hàng tồn nhiều"), и бэкенд должен это сохранять.

## 3. Инфраструктура и Деплой
*   **Frontend**: Остается "слепым пятном". Нет `Dockerfile` для фронтенда, он не поднимается в `docker-compose`. Без рабочего фронтенда повар не сможет верифицировать заказ (кнопка в боте ведет в никуда).

## 4. План действий по приведению к Спецификации v1.0

### Этап 1: Исправление "Мозга" (Priority: Critical)
1.  **Update Config:** Добавить множитель `SAFETY_STOCK_RATIO = 1.1`.
2.  **Update Engine:**
    *   Внедрить формулу: `(Plan * Safety) - Stock - Transit`.
    *   Добавить логику `Packaging` (конвертация в коробки).
3.  **Update Data Loader:** Адаптировать парсер под структуру новой Google Таблицы (нужно четко зафиксировать формат).

### Этап 2: Интеграция Фронтенда (Priority: High)
1.  Настроить сборку Vue.js приложения.
2.  Интегрировать раздачу статики через FastAPI или Nginx.
3.  Развернуть WebApp, чтобы кнопка в боте стала функциональной.

### Этап 3: Обработка Аномалий (Priority: Medium)
1.  Расширить API endpoint `/orders/{id}/confirm` или `/update`, чтобы принимать список изменений с причинами (`reason`).
2.  Обновить `OrderService` для записи реальных причин в таблицу `anomalies`.

---

**Итог:** Система имеет правильный скелет, но нуждается в серьезной доработке бизнес-логики для соответствия реальным процессам ресторана (учет "в пути", коробки, страховой запас).
