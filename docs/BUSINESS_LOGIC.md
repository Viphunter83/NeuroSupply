# Спецификация бизнес-логики NeuroSupply (v1.2)

**Статус:** Текущая рабочая логика (Гибридная модель Таблицы-БД)  
**Архитектура:** Python Backend (FastAPI/SQLAlchemy) + Google Sheets (Панель управления) + Telegram Mini App (Пользовательский интерфейс)

---

## 1. Обзор системы
NeuroSupply — это **система прогнозного пополнения запасов**, предназначенная для автоматизации заказа продуктов в ресторанных сетях. Система использует «гибридный» подход: Google Таблицы служат основным интерфейсом для менеджеров (мастер-данные и планирование), а Telegram — интерфейсом для персонала (исполнение и верификация).

### Основная философия
*   **Модель «Pull»:** Данные синхронизируются из внешних источников (iiko, Таблицы) по расписанию, а не в режиме реального времени. Это экономит ресурсы и квоты API.
*   **Декомпозиция «Деньги в Ингредиенты»:** Прогнозирование начинается с финансового плана (рубли) и разлагается до веса сырья (кг).
*   **Управление через таблицы:** Сложные настройки (страховой запас, продуктовый микс, планы) управляются в привычной среде Excel.

---

## 2. Роли и интеграционные узлы

Система связывает четыре ключевых сущности. Для каждой определены точки входа и функциональные границы:

### 🟢 Бэкенд (AI-Core)
*   **Роль**: "Мозг" и автоматизатор. Не имеет собственного UI для повара, работает как API-сервер.
*   **Функционал**: Синхронизация данных, математический расчет заказа, генерация Excel-файлов, отправка уведомлений в Telegram.
*   **Интеграционный узел**: REST API (FastAPI) + Фоновые задачи (APScheduler).

### 🟢 Google Таблицы (Панель управления)
*   **Роль**: Интерфейс настройки и планирования для Менеджера.
*   **Функционал**: 
    - Ввод плана продаж (выручка/день).
    - Настройка "Продуктового микса" (какие блюда сколько продаются).
    - Установка параметров логистики (Дни в пути, Страховой запас).
*   **Взаимосвязь**: Мастер-система для параметров расчета. Если данных нет в таблице — расчет невозможен.

### 🟢 Telegram Mini App (Операционный UI)
*   **Роль**: Интерфейс исполнения для Повара.
*   **Функционал**: 
    - Визуализация черновика заказа (получение данных из БД через API бэкенда).
    - Ручная корректировка количеств (с обязательным комментарием).
    - Финальное подтверждение, которое меняет статус в БД на `VERIFIED`.
*   **Взаимосвязь**: Без подтверждения в Mini App заказ считается "недействительным" для закупки.

### 🟢 iiko (Провайдер данных)
*   **Роль**: Источник фактического состояния (Sales Fact, Stock Fact).
*   **Функционал**: 
    - Предоставление техкарт блюд (ингредиенты).
    - Предоставление остатков на складах в реальном времени.
    - История чеков для дообучения AI-прогнозов.
*   **Интеграционный узел**: iikoTransport API (v1).

## 3. Архитектура потоков данных

Система работает на трех основных уровнях данных:

1.  **Мастер-данные (Справочники)**
    *   **Источник:** iiko (через API) и Google Таблицы (Вкладки 3, 5).
    *   **Состав:** Техкарты (рецепты), Продуктовый микс (структура спроса), Настройки ресторана.
    *   **Частота синхронизации:** Ночью (04:00 AM).

2.  **Плановые данные (Цели)**
    *   **Источник:** Google Таблицы (Вкладка 2 «ПЛАН ПРОДАЖ»).
    *   **Состав:** Дневные прогнозы выручки (в рублях) на периоды T+1, T+2.
    *   **Использование:** Входные данные для расчетного движка.

3.  **Операционные данные (Состояние)**
    *   **Источник:** БД (Остатки на складе), iiko (История продаж).
    *   **Состав:** Текущий остаток (виртуальный), товары в пути, фактические продажи.

## 4. Алгоритм: Декомпозиция «Деньги в Ингредиенты»

Основная логика ([CalculationEngineV2](file:///Users/apple/NeuroSupply/src/services/calculation/engine_v2.py#16-201)) трансформирует финансовый план в заказ поставщику:

1.  **Вход:** `План продаж (руб)` (из Вкладки 2).
2.  **Декомпозиция (Деньги -> Блюда):**
    *   Используется **Продуктовый микс** (Вкладка 3).
    *   *Формула:* `Кол-во блюд = (План / 1000) * Вероятность * AI_Множитель`
3.  **Взрыв (Блюдо -> Ингредиент):**
    *   Используются **Техкарты** (из БД/iiko).
    *   *Формула:* `Вес нетто = Кол-во блюд * Вес на порцию`
4.  **Анализ дефицита (Потребность -> Заказ):**
    *   **Страховой запас:** Динамический коэффициент из Вкладки 5 (например, 1.1x).
    *   **Остаток:** Вычитается текущий верифицированный запас.
    *   **Транзит:** Вычитаются заказы, созданные за последние 24+ часа.
    *   *Формула:* `Заказ = (Потребность * Страховой_запас) - (Остаток + Транзит)`
5.  **Округление:**
    *   Округление вверх до ближайшей упаковки поставщика (например, коробка 10 кг).

## 5. Дневной цикл работы (Расписание)

Система работает по строгому «Ночному циклу», чтобы заказы были готовы к приходу менеджера утром.

> [!NOTE]
> Указанное время (04:00 и 06:00) является предварительным и может быть изменено в процессе отладки.

### Фаза 1: Ночная синхронизация (04:00 AM)
*   **Цель:** Обновить все мастер-данные (меню, рецепты, планы).
*   **Действие:**
    1.  Подключение к Google Таблицам всех ресторанов (30+ точек).
    2.  Загрузка **Продуктового микса** (Вкладка 3): Обновление структуры спроса.
    3.  Загрузка **Настроек** (Вкладка 5): Обновление страхового запаса и параметров логистики.
    4.  (В планах) Загрузка **Техкарт** из iiko, если изменился хеш состава.

### Phase 2: Расчет и генерация (06:00 AM)
*   **Цель:** Создать черновик заказа на день.
*   **Действие:**
    1.  Чтение **Плана продаж** на сегодня/завтра из Таблицы (Вкладка 2).
    2.  Запуск **Расчетного движка**.
    3.  **Выход 1:** Запись в БД (Заказ #12345, статус `DRAFT`).
    4.  **Выход 2:** Обратная запись в Google Таблицу.
        *   Заполнение **Вкладки 4 «ЧЕРНОВИК ЗАКАЗА 🛒»**.
        *   Заполнение **Вкладки 2a «РАСЧЕТ БЛЮД 🍱»** (для контроля точности).
    5.  **Уведомление:** Бот отправляет сообщение повару: "✅ Заказ на сегодня сформирован. Проверьте в приложении."

### Phase 3: Верификация и исполнение (09:00 AM - 12:00 PM)
*   **Участник:** Повар / Линейный персонал (Обязательный этап).
*   **Инструмент:** **Telegram Mini App** (Смартфон).
*   **Действие:**
    1.  Получает уведомление о готовности черновика.
    2.  **Открывает Mini App:**
        *   **Интерфейс:** Видит *только* сформированный список ингредиентов (Продукт, Ед. изм., Кол-во). Никаких лишних графиков.
    3.  **Проверка «глазами» (Inventory Check):**
        *   Повар проверяет холодильник/склад.
        *   Если видит неучтенный остаток (например, привезли вчера без накладной), корректирует цифру заказа.
    4.  **Подтверждение:**
        *   Нажимает кнопку **«ПОДТВЕРДИТЬ»**.
        *   Статус заказа в БД меняется на `VERIFIED_BY_COOK`.
    5.  **Итог:** Только верифицированные заказы уходят поставщикам.
    6.  **Обратная связь:** Система обновляет Вкладку 4 в Таблице финальными (подтвержденными поваром) цифрами.

## 6. Технические особенности (v1.2)

*   **Изоляция данных:** Каждый ресторан имеет свою выделенную Google Таблицу. Это исключает риск того, что один повар случайно изменит план другого ресторана.
*   **Прозрачность (Feedback Loop):** Система — это не «черный ящик». Вкладка 2a «РАСЧЕТ БЛЮД» показывает математику: «Мы заказали 40кг говядины, потому что вы планируете продать 300 порций Фо Бо». Это повышает доверие персонала.
